# 第六步：从单一异常分析扩展到电商经营调查助手

## 本轮交付范围

V0.4 有三个可执行入口：销量变化调查、库存与缺货查询、活动状态查询。共享商品目录、日期解析、任务持久化、证据、事件与网页工作台。当前全部为只读流程，网页和路由都不调用模型。原 CLI 模型工具循环保留，但这次没有执行真实模型请求。

| 入口 | 示例 | 实际执行 |
| --- | --- | --- |
| 销量变化调查 | 怦然心动2026-10-23销量下降原因 | 四类来源 + 指标分析；满足条件才追加渠道查询 |
| 库存与缺货查询 | 炽热爱意2026-10-23缺货多久 | 仅查询库存来源，不查询销售/流量 |
| 活动状态查询 | 温柔时光2026-10-23活动结束了吗 | 仅查询活动来源 |
| 混合请求 | 怦然心动2026-10-23销量下降，顺便查库存 | 先选择一个事项，再提交；不会把全部分支跑一遍 |
| 不支持的写动作 | 销量下降，顺便退款 | 拒绝；选择其他意图也不能绕过边界 |

“有货吗”也需要明确历史日期；数据只有日级缺货时长，没有实时库存件数。活动查询只有日级活动开启状态，没有完整优惠规则、折扣金额或经营收益。

## 先学这一条完整链路

```text
用户问题
  → routing.route_question：识别只读意图/多意图/不支持
  → task_parser.parse_task：SKU、日期、必要数据校验
  → web_service：保存任务，ready 才排队
  → workflows.execute_task：按白名单分发
     ├─ 销量调查 → 原 runner → 四源分析 → 条件满足才追加一次渠道查询
     ├─ 库存查询 → 只允许库存工具
     └─ 活动查询 → 只允许活动工具
  → 报告、证据哈希、事件、原问题任务卡
```

路由与参数解析是不同阶段。第一阶段知道“查库存”不等于知道查哪个 SKU、哪天。混合意图先选路由，商品歧义再选规格；两种澄清都不能默默猜一个分支执行。

## 模板怎么映射到你的项目

| 面试问法 | 当前真实实现 | 尚未实现 |
| --- | --- | --- |
| 是所有请求都交给模型吗 | 否。三个只读意图先用规则处理，记录 matched_rules 和 reason | 向量、小模型与大模型级联路由 |
| 歧义怎么办 | 返回候选事项/商品，用户确认后以 parent_id 建关联任务 | 通用自由文本多轮指代解析 |
| 模型选错会不会执行危险动作 | 当前路由不调用模型；分发白名单和工具权限仍独立校验 | 退款、补货等写操作审批 |
| 怎么控制调用成本 | 专项查询各 1 次工具；销量基础 5 次，渠道最多追加 1 次；路由模型调用 0 次 | 真实模型 token/费用对比与线上负载优化 |
| 怎么验证准确性 | 48 条人工路由回归；精确率、召回率、混淆矩阵、拒绝误放行数；57 项功能测试 | 独立盲测集、线上用户分布和 A/B 测试 |

规则回归通过不代表开放域自然语言理解准确。有限否定、关键词与并列句识别仍会有误判，需要持续收集新样例。现在规模很小，先用测量结果决定是否需要更复杂的路由层，而不是为了简历加入所有模型。

## 为什么追加调查有工程意义

原先每次固定查询四类数据。现在基础分析后会保存一个 follow_up_decision 事件，包含是否执行、理由和最多追加次数。

1. 有来源冲突：停止自动深挖，优先核对口径。
2. 命中流量相关信号且没有已知冲突：允许一次 get_channel_breakdown。
3. 不满足条件或预算耗尽：不查询渠道。
4. 渠道明细缺失：记录 insufficient_data，保留基础分析。
5. 渠道口径或合计不一致：记录 conflicting，不生成渠道变化结论。

追加明细仍由确定性策略决定，不是模型自主规划。可以将其称为“有界、条件触发的调查工作流”，不能称为已验证的自主多 Agent 根因分析。

样例中商品 UV 从 1000 降至 500，自然搜索归因人数从 500 到 150，付费广告从 300 到 150，推荐维持 200。这只能描述来源变化，不证明投放或搜索变化导致销量下降。

## 新增渠道数据的业务契约

`traffic_channels` 是 schema_version=1 下的可选扩展，旧四表 JSON 仍可读取。缺少扩展时，渠道追加调查会明确说明缺数据。

```json
{
  "sku_id": "FLR-ROSE-19-BOUQUET",
  "date": "2026-10-23",
  "source_id": "synthetic-exclusive-channel-attribution",
  "observed_at": "2026-10-24T08:00:00+08:00",
  "status": "ok",
  "attribution_policy": "exclusive_last_touch_v1",
  "attributed_visitors": {"自然搜索": 150, "付费广告": 150, "推荐": 200}
}
```

普通渠道 UV 可能重叠，不能直接相加。本项目要求每个访客只归到一个末次渠道；两日渠道集合一致，且各日合计等于商品 UV，才计算变化。真实平台不满足这个口径时，应换用合适的分析契约，不能为了跑通而强行分摊。

## 推荐阅读顺序与练习

1. `routing.py`：给三个意图各写三种说法，先预测结果，再运行 route 命令。重点看因果提及与独立并列查询的区别。
2. `task_parser.py`：观察路由选定后，商品歧义、日期缺失、必要来源缺失为何仍会阻止执行。
3. `workflows.py` 和 `tools.py`：验证库存专项只允许库存工具；即使直接调用 Registry，销售工具也被拒绝。
4. `runner.py` 和 `follow_up.py`：沿 follow_up_decision → 工具结果 → 合计校验 → 停止状态，理解有界调查。
5. `evaluation.py` 与 `data/routing_eval.json`：添加没见过的表达，保留错误样例，不能只挑通过的例子汇报。

运行示例：

```powershell
python -m ecommerce_agent route "查销量，顺便查库存"
python -m ecommerce_agent ask "炽热爱意2026-10-23缺货多久"
python -m ecommerce_agent ask "温柔时光2026-10-23活动结束了吗"
python -m ecommerce_agent ask "怦然心动2026-10-23销量下降原因"
python -m ecommerce_agent ask "怦然心动2026-10-23销量下降，顺便查库存" --intent query_inventory
python -m ecommerce_agent evaluate-routing
python -X utf8 -m unittest discover -s tests -q
```

评测报告默认保存在 `runs/evaluation/routing-evaluation.md` 和 JSON 明细。命令行 investigate/demo 保留旧固定流程，ask 和网页通过新分发器；不能把旧 demo 当成新增动态分支已经执行的证据。

## 后续真正值得补的两步

- 数据接入：CSV 导入和质量报告，再接一份来源明确的外部数据；不要将合成样例改标签冒充真实店铺数据。
- 模型效果：为复杂表达接受限模型路由/调查策略，和规则基线对比误路由、澄清率、工具次数、耗时、费用与证据支持程度。没有真实评测前，不声称模型带来提升。

这两项是后续计划，本轮没有实现。订单、退款、CRM 写操作也没有加入。
