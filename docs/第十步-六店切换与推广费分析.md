# 第十步：六店切换与推广费分析

## 用运营的工作方式组织界面

左侧选择门店，再选择经营调查或推广分析。门店命名采用城市＋区/街道：深圳南山店、重庆南岸店、郑州唐人街店、成都玉林路店、成都春熙路店、深圳福田店。它们是可修改的学习配置，不声称是真实营业分店。

花仙女品牌参考来自用户提供的图片。界面只使用花瓣与断弧轮廓，重新绘制成透明SVG，搭配暖金色导航、图表与小图标；没有把原黑底方图放到界面，也没有复制注册标记。助手昵称为“小艾”。源文件是 `ecommerce_agent/web_assets/brand-mark.svg`，主题样式在 `brand.css`。

## 推广分析的口径

| 指标 | 计算与限制 |
|---|---|
| 点击扣费 | 一次广告点击产生费用；UV是去重访客，不能替代广告点击数 |
| 平均CPC | 选定范围总扣费÷总广告点击，不是各小时CPC的简单平均 |
| 推广费用率 | 同店、同日/小时的广告扣费÷店铺支付营业额 |
| 高费用时段 | 费用率严格大于自定义高费用线，默认10% |
| 低投入关注 | 正在投放、有营业额、费用率低于自定义低投入线，默认3%；只表示值得核对 |
| 有扣费无成交 | 营业额为零且仍扣费；比例不可计算，单独提示 |
| 未投放 | 没有开展投放，不因零花费触发低投入建议 |

店铺营业额不是广告归因收入，所以费用率不是ROAS，更不是利润率。没有毛利、退款、履约成本与广告转化延迟，不能据此判断投放盈利。3%只是方便练习的关注线，不是行业标准，也不代表必须增加预算。

小时营业额只保存一份，手动、自动扣费分别保存。筛选其中一种推广时，分母仍是同店店铺营业额，不会把营业额拆成未经证明的广告归因金额。所有金额先以整数分币存储和汇总，再转元展示；阈值判断用未四舍五入的分币数交叉相乘。费用率展示保留两位小数，边界判断可能比显示值更精细。

默认小时账本包含1.00、1.20、1.50、1.80、2.20元等点击单价；当前按“每店、每天、每小时、每种模式固定CPC”生成，不能冒充真实平台实时竞价模型。23时保留有扣费、暂无支付的情形；9–10时低投入；18–19时超过10%费用线。

## 店铺隔离为什么不只做下拉框

`StoreHub` 为每个门店创建独立的 `InvestigationService`：独立输入快照、SQLite任务库、工单、队列和报告目录。请求通过 `X-Store-ID` 指定门店，服务器不维护一个会被不同浏览器相互覆盖的“全局当前店铺”。未知店铺返回400，不偷偷回落到默认店。

任务ID、父任务、工单、材料、复查和下载都在所选店铺范围内读取。另一店铺请求相同任务ID返回404。浏览器切店会清空当前结果、停止旧任务轮询，并使用版本号丢弃切换前的迟到响应。推广筛选请求也有自己的版本号，避免旧筛选结果覆盖新条件。

这仍是共享口令的学习工作区。持口令者可以主动切换六店；逻辑数据隔离不是员工账号、租户权限或RBAC。当前每店一个执行线程，也不是六个自主Agent。

## 文件与调用链

1. `flower_business_data.py`：28款商品、15天基础经营学习数据。
2. `store_workspace.py`：配置六家门店、构造不同规模的经营快照、生成同源小时营业额与点击扣费、绑定独立服务。
3. `advertising.py`：校验店铺、日期、小时、模式、曝光/点击/分币、缺小时与重复行，然后计算报告。
4. `web.py`：鉴权后选择门店，再读取任务、工单或推广报告。
5. `app.js → renderAdvertising`：显示后端结果，做分币转元和图表缩放，不在浏览器重算阈值。
6. `tests/test_stores_advertising.py`：验证跨店不可读取任务、跨店父任务拒绝、费用合计、阈值边界、零分母、缺小时、错误扣费和非法筛选参数。

`/api/stores` 返回门店列表。`/api/advertising?date=2026-10-25&mode=all&high=10&low=3` 返回当前店铺报告，沿用现有Bearer口令与Host/Origin校验。页面可以导出JSON，包含选择条件、小时记录、费用率、注意时段、数据指纹与来源边界。

推广分析目前是独立页面入口，不是新接入大模型的自主投放Agent，也尚未接入自然语言路由。已有四种对话工作流继续服务商品调查/查询；后续可把这里的只读函数包装为推广查询工具，再增加独立路由与缺日期澄清。

## 数据与历史

六店各自保存 `data/stores/<店铺ID>.json` 和 `<店铺ID>-ads.json`。基础经营有393条商品日销售记录，每家店对应15天×24小时营业额、15天×24小时×2种推广记录。小时营业额由同一销售快照精确分配，日合计一致，但分时分配与广告扣费本身均为学习用合成数据，不是实际后台导出。

第一店沿用原学习工作区目录，原先没有门店标签的旧任务保留原冻结数据，不能倒推成该门店真实经营记录。其余五店状态与报告保存在原目录的 `stores/<店铺ID>` 下。重命名建议修改 `STORES` 后重新运行生成器；生成器会覆盖默认经营JSON与六店输入JSON，不修改历史任务快照、工单或报告。

```powershell
python scripts/generate_flower_sample.py
python -m ecommerce_agent web
python -m unittest discover -s tests -q
python -m ecommerce_agent evaluate-routing
```

当前固定数据到2026-10-25，不随日历自动滚动。选择新日期缺账本会明确报错，不把未知花费当零。当前没有真实推广后台、预算修改、出价调整、自动暂停或经营消息发送。

建议练习：先核对深圳南山店25日18–19时高费用，再切重庆南岸店比较；筛到仅手动推广，验证营业额不变而扣费减少；将高费用线改为20%，观察关注时段变化；最后沿着JSON导出的小时字段手算CPC和费用率。
