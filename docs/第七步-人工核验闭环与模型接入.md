# 第七步：人工核验闭环、结果验收与单 Agent 模型接入

## 先回答你最关心的两个问题

**现在不是多 Agent。** 网页是一个执行器管理三条规则工作流。销量、库存、活动是三个业务入口，不是三个独立模型。已有的 CLI 模型模式是单个模型在同一个执行循环中选择受控工具，也不属于多 Agent 协作。

**这一版完成后就可以接真实模型，不需要等多 Agent。** 本轮增加了有限字段验收和同输入对照命令。你在本地配置模型地址、支持工具调用的模型名称和密钥后，可以开始第一轮样例实验。网页仍默认规则模式，不接收或保存 API 密钥。本轮开发只用了协议桩和本地 HTTP 测试，没有调用外部模型。

## 新增的完整业务故事

```text
向阳而生日级记录：全天缺货，但有成交
 → 本轮 Run completed：程序执行完成
 → 自动创建工单 awaiting_human：业务核验未完成
 → 人工填写来源、说明和明确的指标修正
 → 材料追加保存，ready_for_recheck
 → 用户请求复查，rechecking
 → 读取新版本快照，生成关联的新任务和报告
 → 无冲突/缺口且字段检查通过，awaiting_acceptance
 → 用户核对最新报告并填写验收说明，resolved
```

如果只写一句“核实过了”，原指标不变，再调查仍会发现冲突。不能用人工说明直接覆盖客观观察。修正材料也带 `human_supplied_unverified` 标签；字段匹配只能证明计算基于提交记录，不能证明盘点表真实。

`resolved` 表示工单已由工作区操作者验收，不表示销量恢复、因果已证明或平台已完成补货。

## 任务与工单为何分开

| 对象 | 解决什么问题 | 状态示例 |
| --- | --- | --- |
| task / Run | 这次程序执行如何 | queued、running、completed、failed、interrupted |
| review_case | 这件业务核验是否处理完 | awaiting_human、ready_for_recheck、rechecking、awaiting_acceptance、resolved |
| material | 补充了什么以及来自哪里 | 追加记录；修正只作用于后续快照 |

一次工单可关联起始调查和最多三次复查。每份材料都保留，原始输入文件、旧证据和旧报告不改写。工单当前最多追加20份材料，是原型容量边界。

## 数据版本与并发

`task_datasets` 保存任务创建时的数据和商品目录快照；指纹为规范化内容的 SHA256。新任务用自己的快照执行，不从启动后的共享对象偷偷取得另一版数据。

V0.5 调整了恢复策略：有冻结快照的新排队任务可以跨重启按原版本继续；没有快照的旧排队任务遇到版本变化仍中断。在途 Run 不自动重做，关联工单返回人工核验并记录中断事件。它不是跨进程续接模型上下文功能。

每个工单有 `revision`。追加材料、发起复查、验收都必须带当前 `expected_revision`。SQLite 的写事务使两个同版本提交最多成功一次；旧页面、重复点击或旧报告不能覆盖新状态。状态变化与复查任务创建在同一事务中提交。

当前是共享个人工作区：持访问口令的操作者均可处理工单，没有独立审核人身份、RBAC 或店铺租户隔离。

复查保留原任务的业务日期锚点。“昨天”的问题即使几天后才补材料，也仍调查当时解析出的日期，不会把“昨天”重新解释成另一天；复查发起时间另行记录。

## 有限字段验收到底验什么

模型可通过 `finish` 提交：

```json
{
  "summary": "目标日支付件数50，原因仍待核验。",
  "evidence_ids": ["source-1", "source-2", "source-3", "source-4"],
  "assertions": [
    {"evidence_id": "source-1", "date": "2026-10-23", "field": "units_sold", "equals": 50}
  ]
}
```

程序核对本次成功观察中的证据 ID、业务日期、字段白名单、值类型和值。把50说成500、错日引用、未知来源、将 True 当作1都不能通过。模型被拒绝后可以在原步数/时间预算内纠正。

兼容旧模型结果时，未提供断言记为 `references_only`，不冒充字段验收通过。断言通过也只说明所列字段一致，不能证明全部自然语言叙述、因果关系、来源真实性或当前经营效果。

规则模式会导出来源字段断言供复核，这是可追溯检查，不是独立模型效果评测。结果位于 `validation.json`，任务 API 和网页可下载。

## 代码阅读顺序

1. `verification.py`：先读错误值、错日期、假引用为什么被拒绝。
2. `tools.py`：查看 finish 怎样接收有限断言；工具执行权限仍由程序控制。
3. `reviews.py`：重点看 on_settled、add_material、recheck、accept；先理解状态，再看 SQL。
4. `web_service.py`：任务快照、事务内关联工单，以及后台执行后的业务状态结算。
5. `web.py` 与 `web_assets/app.js`：受保护 API、材料表单、最新报告验收与历史时间线。
6. `model_comparison.py`、`provider.py`、`runner.py`：模型请求、工具反馈、字段验收与用量记录。

## 在网页做一次练习

1. 新建调查，点击“数据冲突”样例，提交。
2. 确认“调查完成”与“等待人工核验”同时存在，理解两套状态。
3. 填写说明和来源，选择“库存监测记录”，日期保持 2026-10-23，填缺货120分钟、监测1440分钟。
4. 保存材料，点击“使用补充材料重新调查”。
5. 阅读新报告的人工来源标记和字段验收结果，确认旧报告仍存在。
6. 填写验收说明，明确这是模拟练习，然后关闭工单。

表单目前支持销售、流量、库存、活动四类指标的完整记录修正。渠道扩展材料可经受限 API 提交，但尚无专用渠道编辑表单；没有 CSV/文件上传或真实仓库接口。

## 什么时候、怎么接模型

现在即可从 CLI 开始，用一条固定样例对照，先不改变路由或接入写操作。

1. 复制 `config.example.json` 为 `config.local.json`（已被 Git 忽略）。
2. 在配置中填写你实际服务的 `api_base_url` 和支持工具调用的模型名称。接口必须兼容本项目使用的 Chat Completions 工具协议；不同服务是否兼容需要实际验证。
3. 在本机终端配置 `ECOMMERCE_AGENT_API_KEY` 环境变量；密钥不填进问题、网页、Git 或聊天。
4. 显式执行下面命令。它会向你配置的服务发出请求，可能计费：

```powershell
python -m ecommerce_agent compare-model --config config.local.json
```

对照报告位于 `runs/model-comparison/comparison.md` 和 JSON；两组报告分别在 baseline/model 子目录。两边使用同一固定 SKU、日期和四源工具范围，避免将额外渠道查询差异当成模型优势。

查看：是否完成、工具次数、模型请求次数、实际耗时、字段断言、提供商上报 token。用量未上报时为未知；费用没有接账单/价格源，因此也是未知，不能填0。现有步数和超时限制不是精确的费用上限，单次请求也可能计费。

再人工判断模型是否承认冲突/缺口、是否把相关性说成因果。不要只看语句是否流畅。先完成一次，再增加不同场景的重复实验；不要把协议桩测试写成真实模型效果。

## 单 Agent 与多 Agent 的下一步

建议先验证“单个模型＋受控工具＋程序验收”的价值。之后只有在职责、上下文或权限确实需要分离时，再考虑调查员和复核员等协作角色。评估新增角色时，应同时衡量模型调用、协调、冲突处理和评测成本。

本轮未实现：真实店铺接入、模型路由、多 Agent、模型语义裁判、定时复查、外部通知、补货或改价。核心成果是一个能复现失败路径、保留证据并通过人工核验继续推进的业务闭环。
