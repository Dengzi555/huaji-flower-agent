# 第三步：从命令行调查到可持久化的网页应用

## 先体验

在项目根目录运行：

```powershell
python -m ecommerce_agent web
```

打开 <http://127.0.0.1:8080>，点击“流量下降”样例，再点“开始调查”。结果包含：

- 调查结论：支付件数、访客、支付转化率和候选信号。
- 来源证据：四类来源、日期、状态、证据 ID。
- 执行过程：任务保存、运行开始、工具执行、最终状态。
- 下载报告和完整证据。
- 左侧历史：刷新后依然能查询，不依赖浏览器保存完整结果。

端口被占用时使用 `python -m ecommerce_agent web --port 8081`。终端需保持运行，Ctrl+C 停止。

当前页面用合成样例和规则流程，不发模型请求、不接真实电商平台、不执行改价。已有命令行 agent 模式继续可用，网页尚未开放模型配置。

## 与参考 CRM 相同的架构思想

我们没有复制 CRM 的页面或依赖缺失代码。借鉴的是职责划分：

| 层 | 本项目文件 | 责任 |
|---|---|---|
| 网页工作台 | `web_assets/index.html / style.css / app.js` | 输入问题、选择规格、展示状态/证据 |
| HTTP 接口 | `web.py` | 请求解析、访问口令、响应、固定产物下载 |
| 应用服务 | `web_service.py` | 任务持久化、幂等、排队、后台执行、重启状态 |
| 业务执行器 | `runner.py` | 复用既有的四类工具与调查流程 |
| 业务工具与分析 | `tools.py / data.py / analysis.py` | 数据查询、校验、计算、候选信号 |
| 存储 | SQLite + Run 文件 | SQLite 存任务索引与状态，文件存报告和证据 |

这里没有独立的 Node 前端构建服务：Python 同时提供 HTML/CSS/JS 和 API。这样浏览器请求同一个 origin，本地无需配置跨域。未来换 React 或独立 API 框架时，可以保留业务服务与执行器。

## 学习点一：收到请求不等于完成任务

```text
浏览器 POST /api/tasks
        ↓
解析问题 + 验证 SKU/日期
        ↓
SQLite 事务保存任务
        ↓
返回任务 ID（HTTP 201）
        ↓
后台线程执行 runner.run
        ↓
保存报告 + 更新终态
        ↓
浏览器 GET /api/tasks/<id> 查询结果
```

为什么不在 POST 里一直等？调查可能耗时，浏览器关闭、代理超时或刷新不应该抹掉已接受的任务。

为什么先存数据库再入队？如果只存在 Python 内存，服务退出后用户刚提交的问题就不见了。

这不是分布式任务系统：目前只有一个服务进程、一个后台执行线程。不要同时启动多个进程共用同一数据库。

## 学习点二：区分任务、运行和证据

一个 Web 任务有自己的 task ID，它对应用户问题、解析卡和历史关系。实际执行时，原执行器再生成 run ID，关联工具轨迹、报告和证据。

```text
Task（用户提交）
  ├─ parsed（SKU / 日期 / 比较假设）
  ├─ parent_id（补充信息前的旧任务）
  └─ Run（一次实际执行）
       ├─ Events（工具执行过程）
       ├─ Analysis（确定性计算）
       └─ Evidence / Report（可下载产物）
```

同名商品不会创建执行 Run，而是保存 needs_clarification 任务。点击规格后重新提交，会生成带 parent_id 的新任务；旧问题和它当时缺什么信息都保留。

## 学习点三：幂等键和“再调查一次”不同

同一次提交使用 `Idempotency-Key`。网络重试若带同一个键和同样内容，服务复用已有任务，不再创建第二份。

相同键却带不同内容返回 HTTP 409。用户主动再次调查会使用新键，因此可以生成新任务。

网页会在提交期间禁用按钮；数据库还会用事务保护“查询幂等键→插入”这一段。仅禁用按钮无法防止脚本或网络重试造成重复请求。

## 学习点四：重启后哪些东西还在

默认路径：

```text
web-data/tasks.sqlite3       任务索引、解析结果、状态、事件
runs/web/<run_id>/           调查产物
```

- completed、缺信息、失败等历史：可以继续查询。
- queued：如果数据版本没有变化，重新排入队列。
- running：标为 interrupted，提示重新调查；不声称恢复了原执行进度。
- queued 但数据指纹变化：也标为 interrupted，避免不知不觉更换调查依据。

数据在服务启动时加载为快照；修改原始 JSON 后需重启服务。指纹当前基于文件字节，连格式变化都会被视为新版本，这是一种保守策略。

这是“任务记录持久化 + 明确的重启处理”，不是完整的工具级 checkpoint 恢复。

## HTTP API

| 请求 | 用途 |
|---|---|
| `GET /healthz` | 最小健康状态，无业务数据 |
| `GET /api/meta` | 商品目录、数据日期、样例标识 |
| `POST /api/tasks` | 创建/解析调查任务 |
| `GET /api/tasks` | 最近 100 条任务摘要 |
| `GET /api/tasks/<id>` | 任务、分析与最近 100 条事件 |
| `GET /api/tasks/<id>/artifacts/report.md` | 下载登记在该任务下的报告 |
| `GET /api/tasks/<id>/artifacts/evidence.json` | 下载完整数据观察 |

创建请求只接受 question、可选 sku/date/parent_id。不接受浏览器指定服务器文件路径或模型密钥。

## 本机访问与公网部署分开

默认只绑定 127.0.0.1，不为你创建公网服务。

需要绑定非本机地址时，必须设置至少 24 字符访问口令。例如先在自己的终端生成并设置：

```powershell
python -m secrets token_urlsafe 32
$env:ECOMMERCE_WEB_TOKEN = '粘贴你刚生成的口令'
python -m ecommerce_agent web --host 0.0.0.0
```

浏览器输入同一口令，前端只在当前标签页 sessionStorage 保存，并通过 Authorization Bearer 发送。这里是单操作者访问口令，不是用户账号体系、RBAC 或多租户隔离。不要在没有 HTTPS 的公网链路上输入真实口令和业务数据。

公网落地还需要 HTTPS 反向代理、备份、进程监控与网络配置。本次没有创建公网域名、Cloudflare Tunnel 或外部服务器。

## Docker 运行准备

提供 Dockerfile、compose.yaml 和 .dockerignore。Docker 镜像只复制代码与数据，不带本地配置、历史任务和密钥；任务数据库与报告存到持久卷。

```powershell
Copy-Item .env.web.example .env
# 编辑 .env，将 ECOMMERCE_WEB_TOKEN 填为自己的随机口令
docker compose up --build -d
docker compose logs -f
```

容器内监听 0.0.0.0，但 compose 默认将端口映射到主机 127.0.0.1:8080。仍需在页面输入口令。

```powershell
docker compose down
```

普通 down 不删除命名数据卷；不要随意使用 `down -v`，它会删除数据库和历史产物。备份时应在服务停止后同时保存数据库和报告，不能只复制 SQLite 索引而漏掉证据文件。

Docker 配置是否已实际构建验证，以验证记录为准。源码配置存在不等于已完成容器部署。

## 运行环境的实际边界

- Python 标准库 HTTP 服务适合当前个人项目与受控演示，未做高并发压测。
- 只支持单进程工作队列；扩展多进程需增加可靠队列和任务租约。
- 无登录账号、租户隔离、用户级权限、取消按钮、定时监控或实时模型网页调用。
- 证据是本次观察快照，引用存在性不等于业务因果正确。
- SQLite 保存任务关系，不能把它称为语义 Memory 或向量知识库。
- 本次未新增真实业务数据、经营动作和业务收益指标。

## 怎么读代码

先在浏览器提交样例，然后按这个顺序读注释：

1. `app.js` 的 submit 事件：页面把哪些字段提交给后端？
2. `web.py` 的 do_POST：请求大小、Content-Type、口令在哪里检查？
3. `web_service.py` 的 create：何时保存，何时入队，幂等如何生效？
4. `_worker`：如何复用原 runner，并保存结果？
5. `get / artifact`：刷新后怎样找到历史与报告？
6. `tests/test_web.py`：重启、重复请求、跨站请求分别如何验证？

这次最重要的能力不是“写了一个页面”，而是将业务流程变成一个有任务身份、有持久状态、有可检查产物的服务。
