# 第九步：花店口语、新品与经营数据

## 三个问题，先明确到底缺什么

| 原话 | 商品定位 | 后续动作 |
|---|---|---|
| 99红玫爆款销量下降原因 | 红玫→红玫瑰，99→99朵，结合爆款标签命中炽热爱意 | 日期缺失，先澄清；补充昨天后分析25日对比24日 |
| 33乌梅包括下降原因 | 仅登记的错字短语“乌梅包括”→乌梅玫瑰抱抱桶，33→33朵，命中暮色微醺 | 日期缺失，先澄清；不把任意“包括”都改成抱抱桶 |
| 昨天新上架的洋桔梗销量怎么样 | 品种有三款，结合上架日期2026-10-25缩到云间来信 | 单日销量表现，只读25日销售事实，不算下降比例 |

这里的“昨天”以业务今天2026-10-26为例。数据集固定到25日，日期不会每日自动平移；以后运行时若昨天不在快照内，会返回缺数据，不偷换成25日。学习复盘可把“昨天”改为完整日期。

## 为什么不是让大模型随便猜

`flower_language.py` 保存小型口语词表，输出规范问题与归一规则；`task_parser.py` 将这些依据写入任务卡。原始问题仍保存，纠正不会覆盖用户原话。

解析顺序是：SKU/花名/目录别名候选 → 朵数、品种、容器硬过滤 → 经营标签过滤 → 上架日期过滤。爆款来自目录显式经营标签，不能临时按销量第一名代替。上架日期来自目录，不用销售表第一条记录冒充上架时间。

“洋桔梗昨天销量怎么样”没有指明新上架，仍有三款，要求选规格；同一天若上架两款洋桔梗，也仍然澄清。“多巴胺”“苹果杰克”“紫玫”分别有多个规格，同样不能默认挑第一款。未知错字暂不自动纠正，可以补充词表并加回归用例；当前没有向量检索或模型兜底调用。

## 新品表现和下降原因是两个任务

路由增加 `query_sales_performance`：只调用 `get_sales_metrics`，展示成品件数、支付订单、支付金额，保留来源证据与字段核验产物。它不查齐四类来源，也不声称新品卖得好坏。

`investigate_sales_change` 仍要求目标日和前一日销售基线。云间来信25日刚上架，没有24日记录。如果问下降原因，返回 needs_data；不能把未上架补成零，再制造“无限增长”或“销量下降”。

学习时重点看 `routing.py → task_parser.py → workflows.py`：分别解决“做什么”“查哪个商品和哪天”“只调用哪些工具”。这是四条工作流，当前仍为单个执行框架，不是四个自主 Agent。

## 经营数据如何更像业务

默认 `data/products.json`、`data/sample.json` 由 `flower_business_data.py` 生成，共28款、15个自然日。增加乌梅、洋桔梗、苹果杰克、多巴胺、紫玫、天使之翼、晴天葡萄，以及卡布奇诺、曼塔、海洋之歌、紫霞仙子、白雪山、绣球等店铺商品/系列。系列命名不代表植物学品种认证。

- 爆款：更高访客与成交，99红玫在24→25日访客1267→1193、支付订单61→24，同时缺货17→487分钟；只能称相关信号。
- 乌梅抱抱桶：24→25日访客387→143、支付订单17→6，继续核对渠道来源。
- 新品：云间来信25日上架，137 UV、3笔订单，成品件数可能不同于订单数。
- 长尾：晴天葡萄有曝光但连续零成交；蓝绣球25日零曝光零成交，分母为零时转化率未知。
- 数据质量：保留心动满怀库存缺失/流量延迟、向阳而生全天缺货记录与成交冲突，训练缺失与脏数据处理。

UV、订单数、买家数、成品件数均为整数；不规则数字不等于小数计数。金额包含分币与优惠差异；支付买家数可能小于订单数，一单也可能有多件。渠道采用互斥归因，渠道人数合计等于当日UV。

价格是教学设定，未采用附件的花材批发价格；未建成品花材配方、损耗或利润模型。库存仍是日级成品可售监测，不是实时花材枝数；履约、配送范围、营业时段尚未接入。

## 数据来源与界面文案

主界面使用“经营快照”“新品销量”等业务措辞，不反复显示“模拟”。数据说明与文件元信息保留“学习用合成数据、非真实店铺记录”，`sample_data=true` 不改成false；报告也保留来源说明。练习数据不能作为真实经营经历或上线效果写入简历。

原 `fixtures.py` 的5款、2天小数据集用于稳定算术回归，和经营快照分开。旧测试改为在临时目录生成配套目录，避免依赖运营数据文件。新增 `tests/test_flower_business.py` 验证简称、新品、未知错字、歧义、缺基线、零值和渠道加总。

```powershell
python -m ecommerce_agent ask "99红玫爆款2026-10-25销量下降原因"
python -m ecommerce_agent ask "33乌梅包括2026-10-25下降原因"
python -m ecommerce_agent ask "2026-10-25新上架的洋桔梗销量怎么样"
python -m ecommerce_agent ask "晴天葡萄2026-10-25销量怎么样"
python -m unittest discover -s tests -q
python -m ecommerce_agent evaluate-routing
```

运行 `python scripts/generate_flower_sample.py` 从新的经营生成器重建默认两份JSON，会覆盖这两份文件；原文件已备份于 `artifacts/before-business-v07`。历史任务快照和报告保留，复查继续使用原任务冻结版本。

建议练习：给同一天再加一款洋桔梗，观察请求变为澄清；添加一条你常用的店铺简称并配套失败用例；沿着零成交商品的报告，确认程序没有把零值解释成数据缺失。
