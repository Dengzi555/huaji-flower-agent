# 第二步：把用户问题变成可执行任务

## 这一步解决什么

第一版的调用者必须自己填写 SKU 和日期。第二步增加任务解析层，让用户可以输入：

> 帮我查怦然心动2026-10-23销量下降原因。

系统先确定“查什么”，再进入数据查询。名称解析不是销量/流量的数据转换：它处理的是用户语言和业务标识之间的映射。

```text
用户问题
  ↓ cli.ask
商品目录匹配 + 日期解析 + 能力范围检查
  ↓ task_parser.parse_task
任务卡（ready / needs_clarification / needs_data / unsupported）
  ↓ 只有 ready 可以继续
runner.run（固定 SKU 和日期）
  ↓
四类工具 → 确定性计算 → 证据与报告
```

## 先运行四个例子

### 1. 唯一名称、完整日期：可以直接调查

```powershell
python -m ecommerce_agent ask "帮我查怦然心动2026-10-23销量下降原因"
```

“怦然心动”匹配 FLR-ROSE-19-BOUQUET；目标日为 10 月 23 日，对比日为 10 月 22 日。任务卡 ready，然后调用原来的四类工具。

### 2. 同名商品：先消歧

```powershell
python -m ecommerce_agent ask "红玫瑰花束2026-10-23销量下降原因"
```

目录同时存在99朵和19朵红玫瑰花束规格，所以返回 needs_clarification，并列出候选。

用下一条命令明确规格：

```powershell
python -m ecommerce_agent ask "红玫瑰花束2026-10-23销量下降原因" --sku FLR-ROSE-19-BOUQUET
```

当前是一次一条 CLI 请求，不是有跨轮记忆的聊天。上次问题不会被暗中保留，需带着原问题重跑并补参数。

### 3. “昨天”：必须有可解释的时间锚点

```powershell
python -m ecommerce_agent ask "怦然心动昨天销量下降原因" --today 2026-10-24 --preview
```

预览只生成任务卡；--today 是显式模拟时钟。默认时钟是北京时间真实日期。相对日期解析使用真实日期，不使用样例最新日期。

样例只有 10 月 22 日和 23 日。若运行当天是 10 月 25 日，昨天应解析为 24 日，并因缺数据停止；这种停止是正确行为。

### 4. 超出范围：不能偷换成能运行的任务

```powershell
python -m ecommerce_agent ask "怦然心动上周销量下降原因"
python -m ecommerce_agent ask "怦然心动2026-10-23销量下降，直接改价"
```

第一版不支持周区间，工具也没有改价能力，返回 unsupported。拒绝某个请求不代表程序异常。

## 任务卡长什么样

```json
{
  "parser": "deterministic_rules_v1",
  "raw_question": "怦然心动昨天销量下降原因",
  "business_today": "2026-10-24",
  "timezone": "Asia/Shanghai",
  "intent": "investigate_sales_change",
  "status": "ready",
  "sku_id": "FLR-ROSE-19-BOUQUET",
  "target_date": "2026-10-23",
  "comparison_date": "2026-10-22",
  "comparison_policy": "previous_calendar_day"
}
```

完整文件还包括候选商品、问题列表、比较假设与模拟数据标签。任务卡是结构化执行契约，不是模型的思维过程。

| 状态 | 含义 | 是否调用业务工具 |
|---|---|---|
| ready | 唯一 SKU、明确的完整日、销售比较数据可用 | 是；--preview 除外 |
| needs_clarification | 名称/日期有歧义或信息缺失 | 否 |
| needs_data | 对象和日期已确定，但缺销售基线/目标日 | 否 |
| unsupported | 不是支持的单日销量调查，或涉及写动作 | 否 |

CLI 退出码：0 为成功/可执行预览；1 为调查执行未完成；2 为文件或参数错误；3 为解析待确认、缺数据或超出范围。

## 商品目录为何独立

打开 `data/products.json`：每个 SKU 有 name、variant 和 aliases。

销售记录回答“这个 SKU 卖了多少”，目录回答“用户说的怦然心动是哪一个 SKU”。职责分开，后续才能更换真实商品系统，而不在解析器里写死业务名称。

当前按明确 SKU 或名称/别名匹配；更长、更具体的别名优先。同名商品保留多个候选。它不理解任意错别字、指代或组合属性，也没有语义检索。

## 按这个顺序读有注释的代码

1. `cli.py → main / ask`：一句输入从哪个命令分支进入？
2. `task_parser.py → ProductCatalog.match`：为什么不能默认取第一个商品？
3. `task_parser.py → parse_dates / parse_task`：时间锚点、日期歧义和比较口径怎么确定？
4. `runner.py → run`：只有 ready 的任务才能执行；原问题怎样进入请求记录？
5. `tools.py → ToolRegistry.execute`：为什么模型不能在工具参数里换 SKU？
6. `data.py → DataStore.query`：缺失观察和数值零有何区别？
7. `analysis.py → analyze`：转化率怎么算？候选信号为何不是因果结论？
8. `provider.py → ChatProvider.complete`：模型请求与业务执行如何分离？
9. `tests/test_task_parser.py`：正常、歧义、缺数据和越权请求分别如何验证？

注释重点解释职责、输入输出、业务口径和失败边界，避免只翻译 Python 语法。项目根目录 AGENTS.md 保留了这项约定，后续新增代码也沿用。

## 可选：让真实模型进行后续调查

```powershell
python -m ecommerce_agent ask "怦然心动2026-10-23销量下降原因" --model-config config.local.json
```

任务解析仍由规则完成，模型只在任务 ready 后选择数据工具。--model-config 只读取模型配置和预算；数据/目录/目标日期仍来自 ask 参数及任务卡，不使用配置里旧的 sku_id 覆盖用户请求。没有配置时不会消费 API。

## 边界和下一步

当前实现：有限中文表达、单 SKU、完整自然日、前一日对比、目录别名匹配、任务卡、明确拒绝/缺口。不是通用 NLU，不是多轮会话，也没有新增电商平台接口或 Craft 集成。

下一步的学习任务：新增一个自己的模拟商品及其别名，故意让两个规格共用一个名称，分别观察唯一匹配与歧义结果。然后考虑“商品名称拼错”或“这款商品”需要什么新增检索和会话机制，不要先通过盲猜来跑通。
