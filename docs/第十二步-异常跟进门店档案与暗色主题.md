# 第十二步：异常跟进、门店档案与暗色主题

## 为什么撤下通用Mission入口

花店运营每天更常见的动作是“切店看异常、查证据、记录处理、看新数据”。上一版Mission要求先写长期目标和验收条件，再手动续跑，增加了操作成本。这次把入口改为六店经营概览、经营调查、推广分析、异常跟进、门店设置。

旧Mission、记忆、任务与报告仍在原数据库中，历史快照不修改。旧接口仅为兼容保留，页面不再要求填写通用记忆；新任务的store_memory_snapshot为空，改为保存operating_settings_snapshot。原来积累的推测不会暗中变成新调查的事实。

## 新的运营流程

```text
六店概览 → 进入门店 → 查看调查/推广异常 → 一键加入异常跟进
                                                ↓
                                  记录处理 → 已处理待复查
                                                ↓
                                   读取后续日期新数据
                                                ↓
                       未达标/缺数据继续跟进；达标后人工确认指标恢复
```

也可以明确“暂不处理”，或重新打开已收尾跟进。没有创建一个自由文本长期目标的前置步骤。

## 异常从哪里来

- 调查结果：已完成Run里的销量下降、缺货、来源缺失或冲突。
- 推广时段：账本中重新算出的高费用、低投入待核对、有扣费无成交。

浏览器只传任务ID，或推广日期/小时/模式/关注线。服务端从本店已保存的报告或账本读取指标，不允许客户端随便提交一个“销量跌50%”。同一来源重复点击只返回原跟进单，避免重复待办；来源日期、指标、数据指纹和原阈值被冻结。

## 处理说明不是经营动作回执

“已在后台调整自动推广”只表示运营者的记录。本项目没有连接真实推广后台，也不会因为写下说明就执行、批准或证明这次操作。

处理记录、原异常快照和后续复查分开保存。记录处理后清除旧复查结论；再次修改处理方案，也不能沿用修改前的通过结果收尾。

## 怎样判断指标恢复

| 来源 | 本版固定的复查条件 |
|---|---|
| 销量下降 | 后续日期单日销量达到原异常前的基线，四类目标日来源可用、无已知冲突，库存监测覆盖全天 |
| 缺货 | 后续日期全天监测缺货分钟数为0，其他必需来源可用且无已知冲突 |
| 数据异常 | 目标日四类来源可用、监测完整，未发现买家/访客或全天无货与成交冲突 |
| 高推广费用率 | 同一时段有营业额，费用率回到原高费用线及以下 |
| 低投入待核对 | 同一时段仍有投放与营业额，费用率位于原低/高关注线之间 |
| 有扣费无成交 | 同一时段不再扣费，或出现营业额且费用率不高于原关注线 |

复查日期必须晚于异常发生日，且为已结束自然日。缺记录不会补0；未达标也不会自动关闭。即使通过，仍需人工确认“指标已恢复”。这些规则只说明选定单日/时段满足参考条件，不证明长期稳定恢复，也不证明处理动作导致变化。低投入线不是必须加预算的行业标准。

所有金额仍按分币算，阈值判断不依赖四舍五入后的显示比例。新复查证据和原异常记录都留在时间线，能够回看。

当前输入快照固定到2026-10-25。25日发生的异常需要26日或之后的数据，但26日当天尚未结束；当前不能为了演示而冒充已经有了“明天”的结果。可先用23日异常复查25日数据，或后续导入新日期记录。

## 门店档案代替通用记忆表单

每店独立保存营业开始/结束、主推商品（最多10款）、推广高/低关注线和经营约定。营业结束早于开始可以表示跨日营业，全天营业写00:00至24:00。这些时间暂作档案，不会重算历史全天监测或营业额。

关注线会作为该店推广分析的默认值；单次分析仍可临时调整。已有跟进单继续使用创建时的原阈值，防止修改设置后历史判断标准悄悄变化。主推商品不替代用户明确的SKU，也不用于默选一个有歧义的商品。

设置有版本检查与变更事件。新调查保存当时档案版本，旧任务不随新设置变化。经营约定是人工配置背景，不覆盖工具权限或事实证据。

## 六店概览的口径

每店显示营业额、成品销量、较前日变化、推广费用率和当前未结跟进。销售汇总检查应有已上架SKU的记录是否齐全；缺任意必需SKU记录时显示缺数据，不能把缺行当零业绩。前日基线为0时不计算百分比。

待跟进数量是当前未结记录，可以跨经营日期，不是所选日期内新发生异常的数量。六店仍共用一个访问口令，持口令者可以主动切店，逻辑范围隔离不是员工RBAC。

## 暗色主题

右上角切换明亮/暗色，选择保存在本地浏览器。首次未选择时跟随系统偏好。theme.js在首屏设置主题，operations.css定义暖白古金与炭黑亮金两组颜色。

暗色花瓣图标使用独立的brand-mark-dark.svg，填充与描边为#f2d282，品牌和关键导航图标保持亮金。表格、输入框、原始证据、异常提示和数值同时适配，不是仅将背景涂黑。账本正文仍为15px，表头14px，小屏允许在表格容器内横向滚动。

## 建议阅读顺序

1. operations.py：先看create如何从来源建单，再看action与recheck为何分开。
2. web_service.py：看明确门店档案如何冻结进新任务卡；旧通用记忆不再注入。
3. web.py和store_workspace.py：看每次请求选择本店实例、绑定本店账本与概览汇总。
4. app.js：看从推广按钮到跟进单的操作，及切店后丢弃迟到响应的版本号。
5. theme.js、operations.css、brand-mark-dark.svg：看主题偏好、图标替换与不同区域对比度。
6. tests/test_operations.py：读“仅说明不能恢复”“新处理失效旧复查”“缺数不当0”“广告仍超线不恢复”“门店设置版本与范围”等业务测试。

本版没有自动巡店、预算操作或真实经营效果验证；网页与复查仍为确定性只读逻辑，没有新模型调用。
