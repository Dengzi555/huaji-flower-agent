# 第十一步：Mission与门店独立记忆

> 这是v0.9的历史设计记录。v0.10已撤下通用Mission/记忆页面，新调查不再注入这些记忆，改为异常跟进与明确门店档案；旧数据保留。当前操作请看[第十二步](第十二步-异常跟进门店档案与暗色主题.md)。

## 从CRM借什么，怎样落到花店

本次参考了本地 `AiNativeCrm-main/docs/architecture/mission-state.md`。其中最适合迁移的原则是：Mission记录持续的业务目标，Run记录一次执行；一次Run结束后还要复核，不能自动宣布经营目标已达成。

在CRM中，Mission可以围绕商机等待客户/同事回复；在花店中，可以围绕“跟进99红玫销量异常”“复核晚高峰推广费”保存目标、验收条件、期限、运行历史与人工补充方向。这里借鉴边界和状态机，没有把CRM的消息渠道、数据库触发器或完整Agent运行时搬进项目。

现在点击左侧“持续任务与记忆”，每家门店都有独立的Mission和记忆库。

## Mission第一版的真实能力

```text
持续跟进 → 显式开始一轮调查 → 本轮调查中 → 待人工复核
    ↑                                         ↓
补充方向 ← 等待内部信息                人工验收完成 / 取消
```

- 创建时填写标题、经营目标、人工验收条件与截止日期。
- 续跑问题必须明确商品、日期且有必需数据；每轮复用现有只读工作流，保存原问题、任务卡、证据与报告。
- 同一个Mission最多4轮，不允许并行启动两轮。幂等请求ID阻止重复点击/网络重试产生重复Run。
- 目标、运行记录和状态转换保存在SQLite；刷新页面、关闭进程后仍可继续查看。
- 每轮结束后进入needs_review。即使字段核验通过，也需要人工说明验收依据。
- 人工完成标记为human_attested，business_outcome_verified仍为false，不把自由文本里的恢复目标伪装成程序独立核实。
- 补充方向通过追加事件保存，最近三条进入下一轮任务卡；旧轮次任务卡保持原版本。
- 期限与状态在创建Run和后台认领排队任务时重新检查。排队期间取消/过期不会在重启后继续执行。
- 取消会阻止后续续跑。已经开始的只读查询可能仍会返回结果，不能保证中断在途调用；迟到结果不会重开已取消Mission。

尚未实现：定时巡店、自动等待外部数据再唤醒、模型自主拆分长期计划、消息渠道协作、投放后台操作、跨Run模型上下文续接与真实经营效果验证。网页仍为确定性执行，不调用模型。每个门店的独立队列不等于新增一个自主Agent。

## 门店记忆和业务证据必须分开

| 类型 | 例子 | 保存与使用 |
|---|---|---|
| 运营偏好 | 汇报先列指标，再列待查事项 | 人工明确录入，可长期保留或撤回 |
| 经营约束 | 调整预算前要负责人确认 | 人工来源说明，不替代宿主权限校验 |
| 阶段观察 | 23日出现缺货相关信号，仍待核对 | 必须关联本店已完成调查，并设置有效期 |

系统不会自动记住模型输出。所有记忆标为human_supplied_unverified，关联一份报告也不等于文字结论已经被独立证明。过期或撤回的记忆不进入新任务，旧记录和撤回原因仍保留。

新任务将当时有效的本店记忆保存到 `parsed.store_memory_snapshot`，并明确标注memory_policy：它是背景，不是本次销售、库存或推广事实，不能覆盖商品、日期或工具权限。网页规则计算不根据记忆猜原因；未来显式接模型时，记忆可随任务卡作为背景提供，仍需从工具重新读取当日事实。

每店最多20条有效记忆，避免把所有历史无差别塞入上下文。同名同类记忆不直接覆盖：先明确撤回旧记录，再新增，保留变更痕迹。该版本没有向量检索、Mem0或自动知识抽取，不需要因此先引入复杂依赖。

## 为什么切店后不会串用

Mission、mission_runs、mission_events、store_memories、memory_events均位于各门店自己的SQLite数据库。所有接口沿用X-Store-ID和口令检查，不接受客户端传入另一个数据库路径。

创建Run、关联Mission、检查版本/轮数/期限与记录状态在同一事务提交；后台认领与取消共用写锁。另一个门店即使知道Mission或任务ID，也不能在自己的范围内读取或关联。浏览器切店会清除当前对象与轮询，并丢弃迟到响应。

这仍是共享口令的多店学习工作区。持口令的人可以主动切换全部门店，数据范围隔离不能宣传成员工权限/RBAC。

## 代码阅读顺序

1. `missions.py`：先看Missions与StoreMemory两个类，比较持续目标和长期背景的不同职责。
2. `web_service.py`：看create中的_mission参数、冻结的记忆快照、任务/Mission同事务关联，再看_worker如何结算与处理取消/过期。
3. `web.py`：看/api/missions、/api/memory与现有店铺范围如何组合。
4. `app.js`：看loadKnowledge、loadMission与版本号如何避免切店/切任务后迟到响应覆盖新界面。
5. `tests/test_missions_memory.py`：重点看“Run结束仍待复核”“重放只一轮”“旧请求不随新方向改变”“取消/过期排队不执行”“本店记忆快照不影响别店”。

账本字体已单独调整：正文15px、表头14px、关键数字32px，说明文字12–14px，并增强对比度。样式在knowledge.css，不依赖浏览器整体缩放。

## 品牌与美团参考的事实边界

品牌现已纠正为“花仙女”，用户已确认。此前“花仙艾”是识图错误，不能当成原品牌名；新界面和输入快照已修正，历史报告不追溯修改。

用户提供的美团链接在浏览器标签页可观察到店名“花仙女鲜花店（玫瑰花.开业花篮.生日鲜花）”。网页工具无法读取，浏览器商品内容读取持续超时，因此没有导入未经核实的商品名称、价格、规格、月售或经营指标。只保留最少的公开来源记录在data/public_shop_reference.json，未保存链接中的位置或临时追踪参数。

公开商品页面即便可访问，也不能据此得到真实访客、广告扣费、订单明细和利润。当前业务记录仍是学习用合成快照；后续应使用公开可读商品信息或经营者提供的导出文件接入，不能用虚构记录冒充该店后台数据。
