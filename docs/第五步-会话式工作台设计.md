# 第五步：把调查流程组织成会话式工作台

## 为什么这样改

视觉与信息结构参考 [DeepSeek Harness 官方展示](https://www.deepseek.com/en/harness/)。借鉴浅色工作区、会话历史、底部输入和详情面板的组织方式，保留本项目自己的名称与业务流程。没有引入 DSH 运行时或复制它的插件系统；后端依旧是 Python 调查服务。

旧页面以“发起调查”和“调查记录”两块表单面板为主。新版围绕使用过程展开：选择历史或新建调查 → 输入商品变化 → 阅读分析回复 → 查看来源、过程和产物。页面形式像会话，但当前只支持已有的销量调查任务，不是通用聊天机器人，也没有新增模型能力。

## 布局与职责

| 区域 | 用户做什么 | 对应真实数据 |
| --- | --- | --- |
| 左侧调查历史 | 新建、选择历史、刷新 | SQLite 任务列表 |
| 中间会话 | 阅读问题、指标、候选原因、下一步 | 原问题、任务卡、分析结果 |
| 底部输入 | 提问；展开调查范围补 SKU、日期 | 创建任务 API；消歧后保留 parent_id |
| 右侧详情 | 看对象、来源查询状态，下载四类产物 | 工具事件与产物 API |

商品或日期不明确时，系统会展开“调查范围”。选择19朵红玫瑰花束规格后再次提交，创建关联的新任务，原始歧义任务仍保留。这是业务状态机的界面呈现，不是前端猜出一个 SKU。

## 推荐代码阅读顺序

1. `ecommerce_agent/web_assets/index.html`：先看 sidebar、conversation、composer-area、inspector 四个区域。保留原有 DOM ID，让布局变化与后端协议分开。
2. `style.css`：先看顶部设计变量，再看导航、会话、输入区、详情栏和响应式区块。白色留白用于聚焦会话；蓝色用于主操作、选中状态和可操作入口。
3. `app.js`：沿 initialize → selectTask → render 阅读，再看 renderInspector。页面只投影后端状态，不重新计算经营指标。
4. `web_service.py`：对照任务创建、歧义拦截、后台执行与持久化，理解界面与业务职责的边界。

`renderInspector(task)` 从真实 tool_completed 事件读取四类来源状态。“已返回”只代表工具返回了记录；部分记录缺失或延迟时显示“有信息缺口”。跨来源冲突仍在分析结论中说明，不能用四个绿色状态替代数据质量判断。

`setInspector(open, remember)` 区分首次自动展开和用户手动选择，避免后台轮询把用户刚关闭的面板反复打开。新建调查时清除选中任务与详情状态。

所有问题、来源及结果继续通过 textContent 构造 DOM，访问口令继续通过 Authorization 发送。更换界面不改变这些边界。

## 验证与使用

刷新已有本地或 Tunnel 网址即可看到新版，不需要重启 Python。静态资源由服务读取，响应不缓存。

- JavaScript 语法检查通过，原 44 项 Python 回归通过。
- Edge 实测：样例填入问题 → 提交 → 完成 → 查看指标、证据表、来源详情和执行事件。
- 390px 手机宽度实测：页面无横向溢出；歧义商品提示 → 选择19朵红玫瑰花束规格 → 再次提交 → 调查完成。
- 公网首页实测返回新版 HTML。产物下载端点由 HTTP 回归覆盖；本轮浏览器自动化等待下载事件超时，未将其记为浏览器下载验收成功。
- 改版截图位于 `artifacts/workbench-dsh.png`；改版前的三个前端文件备份位于 `artifacts/before-dsh`，均不提交 Git。

练习：自己把右侧某个来源状态追溯到对应事件，再从事件的 evidence_id 找到报告引用。你会发现，真正有学习价值的部分是让每个界面状态都能找到业务依据。
